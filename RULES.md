# RULES — Строгие правила для чата по проекту Pockie RPG

> **Прочитай этот файл ПЕРВЫМ делом.** Это правила работы — нарушение которых
> ломает проект. Если ты (AI) не следуешь правилам — пользователь прерывает чат.
>
> **Контекст — 3 файла (Stage 160, было 7):**
> 1. `RULES.md` (этот файл) — КАК работать: правила, чек-листы, Hi-DPI.
> 2. `PROJECT_PROMPT.md` — КАК УСТРОЕН проект: архитектура, формулы, FSM, файлы.
> 3. `MEMORY.md` — ЧТО случилось: история stage'ей, готчи, баги, реестр идей, план.

## ПРАВИЛО 1 — Контекст: читать перед работой

Перед **каждой** задачей, по порядку:
1. `RULES.md` (этот файл).
2. `PROJECT_PROMPT.md` — полный контекст архитектуры/формул/связей.
3. `MEMORY.md` — начинай с «Текущая версия» и «История Stage'ей», затем ГОТЧИ
   и Реестр идей (чтобы НЕ повторять предложенное).

## ПРАВИЛО 2 — Обновлять документацию после каждой задачи (КРИТИЧНО)

После **каждого** значимого изменения в коде:

1. **`MEMORY.md`** — обязательно:
   - «Текущая версия: vX.Y» (bump: minor для мелких правок, major для фич/баланса).

   - Новые ГОТЧИ — если найдено что-то неочевидное.
   - «Реестр идей» — пометить реализованное `[x]`, добавить новые `[ ]`.

2. **`PROJECT_PROMPT.md`** — только если изменились: архитектура (модуль/связь),

   (FSM), ключевые константы. Мелкие визуальные правки — НЕ требуют, только MEMORY.

Формат: дописывать в нужные секции, не перезаписывать файлы целиком.

## ПРАВИЛО 4 — Витрина на панели превью (ОБЯЗАТЕЛЬНО по завершении)

Проект живёт в сандбоксе с Next.js превью-панелью. Витрина — единственная страница
(`src/app/page.tsx`), которая показывает актуальный архив проекта для скачивания.

**Структура витрины (сверху вниз):**
1. **Header**: название «Pockie RPG (Ninja Wars 2)», текущая версия, тёмный фон.
2. **Hero-блок**: большая кнопка «Скачать pockie_rpg_vXXX.Y.zip (размер МБ)» —
   `href="/pockie_rpg_vXXX.Y.zip"`, download. Один архив = один актуальный.
3. **Карточки изменений** (grid внизу): по одной карточке на последние версии
   (актуальная сверху, максимум 6 карточек). В карточке: версия, дата,
   буллеты изменений (3-6 строк). Данные — из массива в `page.tsx`.
4. **Footer sticky** к низу viewport (`min-h-screen flex flex-col`, `flex-1` контент).

**Стиль: ТОЛЬКО тёмная тема.** Tailwind-цвета: `zinc` (фоны/текст), `emerald`
(акценты успеха), `amber` (кнопка скачать/версия), `red` (багфиксы), `violet`
(новые фичи). **ЗАПРЕЩЕНЫ** `indigo` и `blue` — стилистика проекта (Pockie RPG —
emerald/zinc dark theme).

**Обновление витрины** — финальный шаг каждой задачи:
1. Собрать архив (ПРАВИЛО 5).
2. Положить в `public/`, старые архивы **удалить** (ПРАВИЛО 6).
3. Обновить массив версий в `page.tsx` (+ карточка, + размер архива, + кнопка).
4. Проверить: `bun run lint` чистый; dev-сервер без traceback; прямая ссылка на
   архив отдаёт 200 (`curl -s -o /dev/null -w "%{http_code}" <url>`).

## ПРАВИЛО 5 — Архив: ПОЛНЫЙ, не инкрементный

**Решение зафиксировано: всегда ПОЛНЫЙ архив проекта.** Обоснование:
инкрементальный требует ручного мержа у пользователя и ведения учёта «что было» —
источник ошибок и рассинхронизации версий; полный — один файл, распаковал и играешь.

- Имя: `pockie_rpg_vXXX.Y.zip` (XXX = major, Y = minor). Bump по ПРАВИЛУ 2.
- Содержимое (из корня проекта):
  - `src/pockie_rpg/` — весь код, **БЕЗ** `__pycache__/`
  - `assets/` — спрайты/иконки/фоны (БЕЗ пустых/неиспользуемых папок)
  - `fonts/`
  - `pyproject.toml`
  - `RULES.md`, `PROJECT_PROMPT.md`, `MEMORY.md` (3 контекстных файла — Stage 160)
- **НЕ включать**: `.venv/`, `.ruff_cache/`, `.git/`, `__pycache__/`, `*.pyc`,
  `data/` (сейв создаётся кодом: `SAVE_DIR.mkdir` в save_load.py),
  `scripts/` (legacy), `*.zip`, `.vscode/`, `worklog.md` (внутренний журнал сандбокса).
- Перед zip: убедиться, что `python -m py_compile` прошёл на изменённых файлах
  (нельзя архивировать сломанный код).
- Размер полного архива ~8-12 МБ — приемлемо для `public/`.

5. `dev.log` можно оставить (отладка), но не дублировать.

## ПРАВИЛО 7 — Layering rule (КРИТИЧНО)

```
config → data → combat → game → ui
```

- `config.py` — самый нижний слой. **Импортирует ТОЛЬКО stdlib** (исключение: lazy-import `combat.skill_registry` внутри `_build_skill_config_from_registry()` — легальный workaround).
- `data/` — stdlib + `pockie_rpg.config` (lazy, внутри функций).
- `combat/` — `data/` + `config/`.
- `game/` — `data/` + `config/` (НЕ `combat/` — наоборот: `combat/fighter.py` импортирует `game.state` через `from_player_state`).
- `ui/` — всё.

Циклических импортов нет. Если появился — lazy import внутри функции.
Никогда не пиши `from pockie_rpg.ui.X import Y` в `combat/` или `game/`.

## ПРАВИЛО 8 — Skill registry: data-driven

Новый навык = запись в `combat/skill_registry.SKILL_REGISTRY` — движок подхватит
автоматически, если эффект использует существующий тип (freeze/poison/shield/
cloud/extra_turn/burn/stun). Новый тип статуса: `SKIP_STATUSES`/`DOT_STATUSES`/
`EXTRA_TURN_STATUSES`/`NO_END_DECREMENT_STATUSES` + тик в on_turn_start/end +
(опц.) EventType + UI-оверлей.

## ПРАВИЛО 13 — SWF → PNG: конвейер анимаций костюмов/мобов

Извлечение кадров: `ffdec` (JPEXS) CLI — `java -jar ~/tools/ffdec/ffdec.jar
-export sprite <outdir> <file.swf>` (FFDec 22.0.2 в `~/tools/ffdec`), прозрачный
фон (alpha), нумерация `1.png, 2.png, ...` (digit-only stem), путь
`assets/extracted/<skin>/<action>/N.png`. Hold-дубли таймлайна SWF СОХРАНЯТЬ
(аутентичный тайминг — конвенция ichigo/cloth14).

### Фейсинг спрайтов (КРИТИЧНО — урок Stage 205/207)
1. **Пользователь при передаче файлов ВСЕГДА сообщает, куда смотрят исходные
   спрайты** («влево»/«вправо»). Если не указано — уточнить ДО интеграции.
2. Жёсткое правило боя: **игрок смотрит ВПРАВО** (на врага), **враг — ВЛЕВО**.
3. Если исходник смотрит не туда — **отзеркалить ВСЕ экшены** (idle/attack/
   run/hit/death) **НА ЭТАПЕ ЭКСТРАКЦИИ**: PIL `transpose(FLIP_LEFT_RIGHT)`,
   lossless, попиксельная проверка (flip→re-mirror == original). Не полагаться
   только на runtime-флип (см. п. 5).
4. **ИТОГОВОЕ** (после зеркала) направление записать в `INTRINSIC_FACING`
   (config.py) для КАЖДОЙ папки `<skin>/<action>`. Без записи включится
   alpha-mass эвристика — она **обманывается причёской/хвостом** (Абараи:
   «LEFT» из-за хвоста при лице вправо).
5. **БАЗА СКИНА БЕЗ ЗЕРКАЛА, RUN_BACK — ПО ДВИЖЕНИЮ (Stage 209, финал)**:
   у кастомных скинов (skin_actions задан: cloth14 и все будущие) база
   всегда False (`set_action`, `base_flip`, spawn) — ассеты смотрят
   ВПРАВО на врага «как есть» (зеркало ТОЛЬКО на экстракции, п. 3).
   ИСКЛЮЧЕНИЕ — фаза RUN_BACK: универсальная инверсия
   `seq.flip = not seq.flip` (семантика Stage 207) — боец бежит домой
   ЛИЦОМ ПО НАПРАВЛЕНИЮ движения (P → LEFT, E → RIGHT). История:
   Stage 208 отменял инверсию для скинов («не зеркалится НИГДЕ») —
   пользователь вернул диагноз: «должен смотреть в сторону куда
   бежит» (в v204.1 было правильно). Флип по `INTRINSIC_FACING`
   остаётся для классики: Ичиго (LEFT → флип) и мобов.
6. **НИКОГДА не хардкодить направление по роли** («игрок → flip=True»).
   Источник флипа — `IdleAnimator.base_flip()` / `set_action` +
   RUN_BACK-инверсия в seq (Stage 207/209). Хардкод «игрок → True»
   разворачивал pre-flipped cloth14 спиной к врагу на беге/атаке.
7. **ИНВАРИАНТ ФЕЙСИНГА + F9 (Stage 209)**: ожидаемое направление —
   P → RIGHT / E → LEFT во всех фазах «лицом к врагу»; RUN_BACK — по
   движению (P → LEFT, E → RIGHT). F9-оверлей показывает для каждого
   аниматора: папка | flip | СМОТРИТ X | ожид. Y — факт рядом с
   ожиданием, несоответствие КРАСНЫМ (✗), сходится зелёным (✓); факт
   считается из INTRINSIC_FACING ⊕ flip (не по alpha-эвристике).
   Заголовок оверлея содержит ВЕРСИЮ сборки (GAME_VERSION, Stage 210:
   «F9 FACING v205.1 state=…») — репорт со старой сборки виден сразу.
   Каждое нажатие F9 сохраняет строки оверлея в
   `data/facing_report.txt` И показывает 3с плашку с ПОЛНЫМ путём
   файла (Stage 210) — копипаст-репорт: присылаете текстом,
   разбор за минуту (без скриншотов).
8. Верификация: `scripts/diag_stage210.py` (версия в F9 + репорт-файл
   + плашка + RUN_BACK-регресс), `scripts/diag_stage209.py` (статы
   Абарая + качество костюмов + RUN_BACK-фейсинг + F9-инвариант/репорт),
   `scripts/diag_stage208.py` (обновлён под Stage 209),
   `scripts/diag_stage207.py` (флип по фазам, ichigo/враг 1:1) +
   живая проверка на бою: **F9 — фейсинг-оверлей** (инвариант факт/
   ожидание; репорт в data/facing_report.txt); тест-панель — F8.

## ПРАВИЛО 17 — Костюмы: качество и добавление новых (Stage 209)

**4 тира качества** (как у предметов): Grey (Серый) / Blue (Синий) /
Purple (Фиолетовый) / Orange (Оранжевый). Палитры — `config.py`:

(`_blit_gear_icon`, `_render_outfit_tooltip`, `_render_wardrobe_modal`) —
код при добавлении костюма НЕ трогается.

**Новый костюм = только данные** (Stage 205-209 конвейер):
1. Кадры 5 экшенов → `assets/extracted/<skin>/<action>/N.png`
   (П13: экстракция + зеркало + INTRINSIC_FACING).
2. `config.py`: ACTIONS-таблица + PLAYER_MOTION_SKINS[<skin>].
3. `item_db.py`: OUTFITS_DB[<suit>] = name / archetype / base_stats /
   bmv_price / growth / **quality** / motion_skin=<skin> / suit_id;
   EQUIPMENT_DB[<suit>] = name / icon_filename / **quality** / sell_price;
   (иконка → assets/icons/items/).
4. `roles_db.py`: Suit i29XXXX (avatar/pose/name) + связка suit_id.
5. Статы костюма ВСЕГДА берутся у пользователя (формат: «Сила 26 (+1.3) …
   BMV: 10 силы → 1%…») — не выдумывать.
6. Диагностика: `scripts/diag_stage209.py` секции A (данные) — расширить
   под новый костюм по образцу.

## Hi-DPI — правила работы с нативным рендером (Stage 150-160)

Архитектура и статус миграции — `PROJECT_PROMPT.md` §12.3.1. Здесь — рабочие правила.

### Чек-лист «как мигрировать экран»
1. Все `pygame.Rect` / `draw.*` / `blit` — через `self._su()` / `_su_rect()`.
2. Все шрифты — через `self._su_font(size, bold)` (НЕ `self.font_*` и НЕ
   модульные `SysFont` — они фиксированного размера).
3. Иконки: масштаб через `_su_icon_size` (семантика Stage 142 «кап апскейла
   ×1.3» и Stage 149 «без даунскейла 1:1»), результат кэшировать.
4. Фоны/спрайты с диска — `_su_scaled()` / `_su_image()` (загрузка ОДИН раз,
   кэш по (ключ, размер)). Полноэкранные затемнения — `_su_overlay()`.
5. Layout'ы между кадрами — в нативных координатах; события конвертировать
   (`_inv_native_pos`). Клик-rect'ы помечаются `native=True` автоматически.
6. Регистрация: `NATIVE_MODAL_REGISTRY` += ключ; ветки в
   `_native_overlays_will_render()` / `_render_native_overlays()`; для БАЗОВОГО
   экрана — `_native_base_will_render()` + begin/end-пара в `run()`.
7. Всплывашки экрана (тултипы, меню) — в той же фазе, что и экран.
8. Смоук: `python scripts/hidpi_smoke.py --modal <key>`.

### Критичные готчи нативного пути (нарушение = сдвиг кликов / мыло)
- **REBIND `_click_rects` запрещён в нативной фазе**: `_render_map()` каждый кадр
  делает `self._click_rects = []` — любой индекс, записанный ДО рендера,
  бессмыслен. `_end_native_base_screen()` помечает native=True ВСЕ rect'ы
  текущего списка (фикс Stage 159). Новые базовые экраны — переиспользовать
  begin/end-пару без своих индексов.
- **Всё в нативной фазе — только через `_su()`/`_su_rect()`/`_su_font()`**,
  включая мелочи: кнопка «Карта мира» рисовалась сырым Rect — на 2К висела
  не там и не в том масштабе (Stage 159).
- **Хиттесты вне ClickRect-диспетчера** (реестр `_window_close_buttons`) хранят
  `is_native` и конвертируют дизайн-позицию события ×`_ui_scale`.
- **Высота отрендеренного текста в нативной фазе — НАТИВНАЯ**: если
  `surf.get_height()` участвует в дизайн-арифметике — делить на `_render_scale`.
- **`_present_fullscreen` при нативном базовом экране** НЕ растягивает буфер
  1280×720 (затрёт нативный кадр) — только накладывает legacy-слой.
- **Снапшоты фреймбуфера запрещены**: буфер `_fullscreen_game` не обновляется
  в нативной фазе — Stage 160 перевёл фон боя на ассет локации
  (`_capture_battle_bg_snapshot`).
- **Смоук `hidpi_smoke.py` делает `.clear()` списка ПЕРЕД кадром** — этим
  маскировал rebind-баг: НЕ считать его исчерпывающим для хиттестов; для
